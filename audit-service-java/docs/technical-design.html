Audit Log Service — Technical Design & Implementation

Generated: 2026-09-02T00:03:09-05:00

Scope

This document describes class-level design, implementation details, security considerations, and design decision rationale for the Audit Log Service implemented in the repository path audit-service-java/. The service provides append-only audit events, flexible querying, tamper-evidence through a hash chain, structured redaction, cryptographic erasure, retention (soft-archive), bulk export, and OpenAPI documentation with Swagger UI.

High-level Architecture

Spring Boot application (Java 17) using Spring Data JPA with H2 (runtime) for persistence. Key components:

  • REST API layer: AuditController
  • Service layer: AuditService
  • Persistence: JPA entities (AuditRecord, RedactionRecord) and Spring Data repositories
  • Cryptography: AES-GCM per-record data keys wrapped with a master key
  • OpenAPI documentation served via springdoc

Class-by-class Implementation

1. com.example.audit.model.AuditRecord

Location: src/main/java/com/example/audit/model/AuditRecord.java

Role: Primary JPA entity that represents an audit event in the immutable chain.

Key fields

  • Long id — primary key (IDENTITY)
  • String eventType, actorId, resourceType, resourceId — event metadata
  • String payloadEncrypted — AES-GCM encrypted payload (base64 IV||ciphertext) stored as CLOB
  • String payloadHash — SHA-256 hex of plaintext payload (used in chain computation)
  • String timestamp — ISO-8601 timestamp string
  • Boolean archived — soft-archive flag (nullable to support schema migrations)
  • String archivedAt — timestamp when archived
  • String contentHash — SHA-256 hex of canonicalized content used for chain linking
  • String prevHash — previous contentHash link in chain
  • String encryptedKey — base64 AES-GCM encryption of the per-record data key (wrapped by master key)

Notes

contentHash is computed over a deterministic JSON map containing eventType, actorId, resourceType, resourceId, payloadHash, and timestamp. Using payloadHash (instead of plaintext) permits chain verification without requiring stored plaintext and enables cryptographic erasure.

2. com.example.audit.model.RedactionRecord

Location: src/main/java/com/example/audit/model/RedactionRecord.java

Role: Stores structured redaction actions. Fields include:

  • targetRecordId — id of the record being redacted
  • redactorId — who performed redaction
  • fieldsJson — JSON array of dot-paths (e.g. ["payload.ssn"])
  • originalPayloadHash — payloadHash before redaction (auditable)
  • timestamp

Design: Redactions are stored as separate auditable records and also generate a REDACTION event appended to the chain, preserving the trace even when plaintext becomes irrecoverable via cryptographic erasure.

3. com.example.audit.repo.*Repository

Location: src/main/java/com/example/audit/repo/

  • AuditRecordRepository — extends JpaRepository for AuditRecord. Custom finder: findTopByOrderByIdDesc() used to get latest prevHash.
  • RedactionRecordRepository — extends JpaRepository with findByTargetRecordIdOrderByIdDesc.

4. com.example.audit.service.AuditService

Location: src/main/java/com/example/audit/service/AuditService.java

Role: Core business logic. Responsibilities:

  • append(...) — accept event, encrypt payload with per-record data key, wrap data key with master key, compute payloadHash and contentHash, link prevHash, persist AuditRecord
  • query(...) — flexible filters (actorId, resourceType, resourceId, eventType, from/to) with pagination
  • verifyChain() — iterate all records in ID order and recompute contentHash using stored payloadHash; detect contentHash mismatch or prevHash mismatch and report first break
  • redactRecord(...) — create a RedactionRecord, perform cryptographic erasure of the record's encryptedKey, append REDACTION event
  • eraseRecord(...) — dedicated cryptographic erasure: set encryptedKey=null, append ERASE event
  • applyRedactionView(...) — if payload is decryptable, decrypt payload, apply field-path redaction to produce a redacted plaintext view (returned in API responses when redacted=true)
  • archiveOlderThanDays(...) — soft-archive by setting archived=true and archivedAt
  • exportBundle(...) — build a verifiable export bundle containing selected records and chain metadata (contentHash, prevHash)

Cryptography

Implementation (in AuditService):

  • AES-GCM with 12-byte IV and 128-bit tag (JCE algorithm AES/GCM/NoPadding).
  • Per-record 256-bit data key (random) encrypts payload; ciphertext stored as base64(IV||CT).
  • Data key is wrapped by encrypting it with the master key (AES-GCM) and saved in encryptedKey as base64.
  • payloadHash = SHA-256(hex) of plaintext payload. It's included in chain computation so verification does not require plaintext.

Master key handling

AuditService loads master key from configuration (spring property audit.master-key) or environment variable AUDIT_MASTER_KEY (base64-encoded). If not provided, the service generates a transient 32-byte key (not suitable for prod). Production deployment should use a KMS or secrets vault and inject the base64 key to ensure recoverability across restarts.

5. com.example.audit.web.AuditController

Location: src/main/java/com/example/audit/web/AuditController.java

Endpoints implemented:

  • POST /audit/events — create an event (returns safe view)
  • GET /audit/events — query; supports redacted=true to return decrypted/redacted payloads where available
  • GET /audit/events/{filterField} and GET /audit/events/{filterField}/{value} — path-style filters
  • POST /audit/redact — structured redaction (creates REDACTION event and triggers key deletion for cryptographic erasure)
  • POST /audit/erase — dedicated cryptographic erasure API (deletes encryptedKey and appends ERASE event)
  • POST /audit/archive — soft-archive older records
  • GET /audit/export — export bundle for actorId or resourceId
  • GET /audit/verify — verify chain integrity

Safe API responses

Controller intentionally avoids returning encryptedKey or payloadEncrypted in responses. Instead it returns a safe view containing payloadHash and payloadAvailable. When redacted=true the controller will include decrypted and redacted plaintext in the payload field if decryption is possible; otherwise payload will be null.

Design Decisions & Rationale

Hash chain uses payloadHash

Including the SHA-256 of the plaintext payload (payloadHash) in the canonical content used to compute contentHash allows chain verification without access to plaintext. This design enables tamper-evidence even after cryptographic erasure (keys removed) while preserving privacy.

Per-record data key + master key wrapping

Using per-record data keys (wrapped by a central master key) balances confidentiality (different key per payload) and manageability (only the master key must be stored securely). Erasure is implemented by deleting the wrapped data key. Alternative approaches considered:

  • Store plaintext payload encrypted by a single key — easier but erasure requires rotating or destroying that single key, which may affect multiple records.
  • Use KMS envelope encryption directly for each record — stronger key management but introduces external dependency; current implementation can be adapted to call KMS to encrypt/decrypt data keys.

Redaction approach

Two-layer redaction:

  1. Structured redaction view: when data is available, apply field-level redaction at read-time and return a redacted view. This preserves the original plaintext for audit trail when keys still exist.
  2. Cryptographic erasure: when strong removal is required, delete the wrapped data key. The payload ciphertext remains but is unrecoverable. A REDACTION event and RedactionRecord are stored to document the action.

Trade-offs: storing original ciphertext preserves chain integrity and provable non-retrievability after key deletion — but legal requests may require additional audit artifacts.

Soft-archive vs hard-delete

Records older than a configurable window are soft-archived (flag and timestamp). Archive does not remove records from the chain; verifyChain treats archived records as still part of the chain. This meets requirement that archived records do not cause false-positive chain breaks.

Database & Schema Notes

H2 is used for runtime in local/dev; file-based DB configured in main application.properties and in-memory DB for tests. The archived field was made nullable (Boolean) to ease schema migrations; applications should migrate and backfill before making it NOT NULL in production.

Security Considerations

  • Master key must be stored securely (KMS/vault). If lost, payloads cannot be decrypted.
  • Controller responses never include wrapped keys or ciphertext by default to avoid leakage.
  • Use TLS in transit for all API traffic.
  • Consider RBAC for endpoints that perform redaction or erasure (currently no auth is implemented in this repo).
  • Audit events for redaction/erase include original payloadHash to prove pre-redaction content existed.

Operational Notes

  • To run tests: mvn -f audit-service-java test (ensure AUDIT_MASTER_KEY set or accept ephemeral key).
  • To run app: mvn -f audit-service-java spring-boot:run and open http://localhost:8081/swagger-ui.html.

Limitations & Future Work

  • Master key management should be replaced with KMS; add automated key rotation and key-escrow mechanisms.
  • Add authentication/authorization (RBAC) to protect redaction/erase/archive endpoints.
  • Add deterministic migration scripts and ability to backfill archived flags then enforce NOT NULL constraints.
  • Hardening tests to simulate concurrent appends and large export bundles; performance testing under load.
  • Consider using per-tenant keys in a multi-tenant deployment.
